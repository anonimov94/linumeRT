## Zakres i wynik

Działa pionowy wycinek: rzeczywiste NML LinuxCNC → osobny proces odczytu →
walidowany niezmienny `MachineSample` → niezależny host Qt → odczyty skórek.
Wspólny kontrakt obsługuje wszystkie cztery rodziny. W Qt sprawdzono wszystkie
cztery, z rzeczywistym LinuxCNC/Xvfb sprawdzono Classic Digital.

Widoczne dane: rzeczywista pozycja trajektorii w układzie maszyny G53 (mm/°,
nie offset detalu i nie pozycje stawów), tryb, stan task/interpretera, E-STOP
raportowany przez NML. Maska osi wyłącza odczyty nieistniejących osi; dla maszyny
calowej odczyty liniowe są normalizowane do mm, kątowe niezależnie do stopni.
Nie dodano kanału komend ani obejść QtVCP/ACTION/HAL. Test nie wysyła resetu,
ruchu ani zmiany trybu; E-STOP pozostaje aktywny przez cały odbiór.

`skin-preview.py` pozostaje offline. Nowy `skin-monitor.py` uruchamia osobne
okno obok istniejącego HMI; nie uruchamia sam LinuxCNC ani nie zastępuje ekranu
operatora. Handler produkcyjny, jego interlocki i heartbeat nie były zmieniane.
Alarmy, program, narzędzia, F/S, overrides i sceny 3D pozostają niepodłączone;
monitor nie przedstawia przykładowego G-code ani modeli poglądowych jako danych CNC.
Dekoracyjny czerwony grzyb jest usunięty z monitora; stan E-STOP jest tekstowym
odczytem NML. Przyciski CNC pozostają wyłączone, nawigacja/ustawienia są lokalne.

## API i granice świeżości

Zbadano [dokumentację Python LinuxCNC 2.9](https://www.linuxcnc.org/docs/2.9/html/config/python-interface.html)
i [implementację stat/poll w gałęzi 2.9](https://github.com/LinuxCNC/linuxcnc/blob/2.9/src/emc/usr_intf/axis/extensions/emcmodule.cc).
Użyto wyłącznie `linuxcnc.stat()` / `poll()`; bez `command()`, `error_channel()`
i pinów HAL. `error_channel` jest kolejką konsumowaną, więc jej drugi czytnik
mógłby odbierać komunikaty głównemu HMI. API QtVCP/ACTION pozostaje przyszłym
właścicielem komend; ten etap korzysta bezpośrednio z publicznego API statusu.

Każda próba to świeży proces z nowym kanałem, co izoluje błąd pierwszego tool
mmap LinuxCNC 2.9 i pozwala wystartować monitor przed kontrolerem. QProcess
pracuje asynchronicznie, bez powłoki, najwyżej jedna próba naraz, próby co
200 ms, limit 500 ms. Błąd, uszkodzony JSON, niepoprawne wartości albo wygaśnięcie
kasują cały snapshot i DRO. Prawidłowe próby przywracają widok po restarcie CNC.

**Istotne ograniczenie:** `stat.poll()` w 2.9 nie udostępnia numeru/znacznika
kolejnej aktualizacji producenta. Czas próbki mierzy wykonanie odczytu lokalnym
zegarem monotonicznym, nie dowodzi świeżości danych we wspólnej pamięci NML.
Zamrożony producent może pozostawić poprawnie czytelne stare dane. Monitor
pokazuje ten brak potwierdzenia w globalnym pasku. Snapshot nie trafia do
`switch_gate`, safety ani interlocków i nie może autoryzować ruchu.
Odczyt E-STOP z NML nie jest niezależnym potwierdzeniem sprzętowego safety.

## Odbiór ręczny i następny etap

W tym samym środowisku/NML namespace co działający symulator i główne HMI:

```sh
python3 tools/dev/skin-monitor.py --skin classic-digital --language pl
# Pozostałe: industrial-pro, cyberdeck, organic-vector.
# Offline pozostaje: python3 tools/dev/skin-preview.py --skin classic-digital
```

1. Otworzyć monitor bez CNC: kreski, status niedostępny; przyciski CNC nieaktywne.
2. Uruchomić normalny symulator z głównym HMI: porównać absolutne pozycje G53,
   jednostki, tryb i E-STOP. Nie porównywać z offsetowanym DRO detalu.
3. Zamknąć symulator: sprawdzić wygaszenie, potem uruchomić go ponownie i sprawdzić
   powrót danych. Ustawienia lokalne nie wysyłają komend do maszyny.
4. Zamknąć monitor: główne HMI pozostaje właścicielem sterowania.

Kolejny etap: udokumentowany adapter STATUS w osobnym hoście QtVCP, wspólna
trwała warstwa alarmów i globalnych kontrolek, niezależny dowód świeżości
producenta oraz dopiero potem walidowany kontrakt komend i jego interlocki.
Pełne SKIN-02 oraz SKIN-04…06 pozostają otwarte. Nie przyznaję punktów konkursowych.
**NIEZWERYFIKOWANE NA SPRZĘCIE**; bez odbioru pulpitu i docelowego GPU właściciela.
